### 7.1 ⚠️ 脚本编码陷阱（已踩，务必遵守）
本机默认 Shell 是 **Windows PowerShell 5.1**，它读取 `.ps1` **不带 BOM 的 UTF-8 文件时按 ANSI(GBK) 解码**，
中文注释/字符串会被解成乱码，多字节序列还会破坏引号配对，报出误导性的
`The string is missing the terminator: "` 语法错误（实测 `download_data.ps1`、`train_all.ps1` 均中招）。

**规则**：

1. 任何含中文的 `.ps1` **必须存为 UTF-8 with BOM**（前三字节 `EF BB BF`）。
2. 由于用 `write` 工具生成的文件默认无 BOM，写完 `.ps1` 后必须补 BOM：

   ```powershell
   $enc  = New-Object System.Text.UTF8Encoding($true)   # $true = 带 BOM
   $text = [System.IO.File]::ReadAllText($p, [System.Text.UTF8Encoding]::new($false))
   [System.IO.File]::WriteAllText($p, $text, $enc)
   ```
3. 写完必须做语法自检（不需要执行脚本）：

   ```powershell
   $e = $null; [System.Management.Automation.Language.Parser]::ParseFile($p, [ref]$null, [ref]$e) | Out-Null
   if ($e) { $e[0].Message; $e[0].Extent.StartLineNumber }
   ```
4. 只用 PowerShell 5.1 兼容语法：**不要用** `??`、三元 `? :`、`&&`/`||` 管道链（这些是 7.x 才有）。
5. Python 侧同理：脚本输出中文前设置 `$env:PYTHONIOENCODING='utf-8'`、`$env:PYTHONUTF8='1'`，
   否则中文日志在 5.1 控制台会乱码。
6. 读取由 Python 写入的 UTF-8 日志必须显式指定编码：`Get-Content x.log -Encoding UTF8`，
   否则 PowerShell 5.1 会按 GBK 解码，中文日志显示为乱码（文件本身没坏，只是显示错）。

### 7.2 ⚠️ 缓存目录与日志输出治理（已踩，已加固）

**陷阱 A：不设 `TORCH_HOME` 会写 C 盘并失败**

torchvision / timm 的预训练权重默认下载到 `C:\Users\<user>\.cache\{torch,huggingface}`。
本机 C 盘余量仅约 15 GB；在受限环境下写该路径会直接报
`PermissionError: [WinError 5] 拒绝访问: 'C:\\Users\\11879/.cache\\torch'`，
报错完全指不到真正原因。

→ 加固：`ml/utils.py::ensure_cache_env()` 已在 `ml/train.py`、`ml/evaluate.py` 入口处兜底设置
`PIP_CACHE_DIR / TORCH_HOME / HF_HOME / HF_ENDPOINT` 到项目内 `.cache/` 并自动建目录，
**显式传入的环境变量优先级更高**。因此直接 `python -m ml.train ...` 也是安全的。

**陷阱 B：tqdm 在非 TTY 下刷屏**

tqdm 在后台作业 / 管道 / 日志采集（`stderr` 非终端）下依然逐步输出。
实测 ConvNeXt-Tiny 只跑 40 秒就产生 **157.8 KB** 控制台日志，60 epoch 推算可达 10 MB 级，
会打爆作业输出缓冲区并淹没关键信息。

→ 加固：进度条收敛到唯一实现 `ml/utils.py::make_bar`，默认 `auto` 策略 ——
仅当 `stderr.isatty()` 为真才显示。控制方式：

```powershell
python -m ml.train --config ... --no-progress     # 后台作业推荐
python -m ml.train --config ... --progress        # 本地终端想看进度条时
$env:ML_PROGRESS = '0'                            # 等价的环境变量开关
```

**实测对照**（同一 3-batch 单 epoch）：默认 **3.61 KB** vs `--progress` **18.97 KB**。
后台运行的可靠进度来源是 `ml/outputs/logs/<tag>_train.csv`（逐 epoch 一行）。

### 7.3 ⚠️ `.gitignore` 未锚定的目录规则会误伤子目录（已踩，已修）

**陷阱**：`.gitignore` 里写 `data/`（**不带前导斜杠**）会匹配**任意层级**名为 `data` 的目录，
于是 `backend/app/data/flowers.json`（102 条人工整理的百科数据）被一起忽略，
而它并不是体积大的数据集 —— 差点造成可贵的领域数据丢失。

→ 修复：改为 **`/data/`**（锚定仓库根），并在规则上方写明原因。

**通用规则**：凡是想忽略"项目根的某个目录"，一律加前导 `/`：

| 写法 | 含义 | 风险 |
| --- | --- | --- |
| `data/` | 任意层级的 data 目录 | ⚠️ 会误伤 `backend/app/data/` |
| `/data/` | 仅项目根的 data 目录 | ✅ 正确 |
| `ml/outputs/*` | 已含路径分隔符，天然锚定 | ✅ 正确 |
| `*.db` | 任意位置的扩展名 | ✅ 符合预期 |

**自检命令**（改完 `.gitignore` 必须跑）：

```powershell
git check-ignore -v backend/app/data/flowers.json   # 期望：无输出（= 不被忽略）
git check-ignore -v data/flowers-102/manifest.json  # 期望：输出规则行（= 正确忽略）
git status --short --untracked-files=all            # 确认该入库的都在列表里
```

### 7.4 ⚠️ SQLAlchemy `create_all` 前必须导入模型（已踩，已修）

**陷阱**：`Base.metadata.create_all()` 只会创建"已经注册到 metadata 的表"。
若调用前没有 `import app.models`，`Base.metadata.tables` 是**空的**，于是一张表都不会建，
而且**不报错** —— 在已有数据库的开发机上完全看不出来，部署到全新环境才炸。

→ 修复：在 `app/main.py` 的 lifespan 里显式 `from app import models  # noqa: F401`，
并把建出的表名打进启动日志（`数据表 = flowers, model_metrics, ...`），让"建了 0 张表"一眼可见。

**自检方式**：用一份全新数据库启动服务，确认表被创建：

```powershell
$env:DATABASE_URL = "sqlite:///./backend/_tmp_fresh.db"
python -m uvicorn --app-dir backend app.main:app --port 8011
# 另一终端：确认 sqlite_master 中有 flowers / model_metrics / recognition_records / users
```

### 7.5 ⚠️ GPU 推理延迟：三个必须处理的坑（已踩，已修）

M3-4 首次实测单张 ViT-B/16 推理 **495.7 ms**，远超离线测得的 10.14 ms。
逐步排查出三个独立问题，优化轨迹 **495.7 → 218 → 26.5 ms（首次）/ 13 ms（稳态）**。

#### 坑 A：首次推理冷启动（495.7 ms）

cuDNN 在第一次前向时要选择卷积算法、分配显存、编译 kernel。
→ **在 `InferenceService.load()` 末尾做启动预热**（5 次 dummy 前向）。
不预热的后果是"答辩现场第一张图明显卡顿"，很容易被误判成系统性能差。

#### 坑 B：cuDNN 按显存地址反复重选算法（前几次请求 ~67 ms）

训练侧开启了 `torch.backends.cudnn.benchmark=True`。若每个请求都用新张量，
地址不断变化会触发算法重选，表现为"前几次慢、之后才快"。
→ **复用一块固定输入缓冲区**（`_input_tensor()` 用 `copy_` 原地写入），地址恒定。
注意：预热必须也使用**同一块**缓冲区，否则首个真实请求仍会重选（实测首次 218 ms）。

#### 坑 C：`latency_ms` 计时口径错误（最隐蔽）

两个子问题，都会让报告里的性能数字失真：

```python
# ❌ 错误 1：CUDA 算子是异步的，不等 GPU 算完就停表 → 测到的是 kernel 启动耗时，低估延迟
logits = model(x); probs = softmax(logits)
latency = time.perf_counter() - t0

# ❌ 错误 2：为了修复 1 而在末尾加 synchronize，却把计时**开始前**那次异步 H2D 拷贝
#          也等了进去 → 虚高到 55—65 ms
tensor = tensor.to(device)      # 异步拷贝
t0 = time.perf_counter()
logits = model(tensor); ...
torch.cuda.synchronize()
latency = time.perf_counter() - t0

# ✅ 正确：先冲掉前置拷贝，再计时，末尾 synchronize
tensor = tensor.to(device)
torch.cuda.synchronize()        # 冲掉拷贝
t0 = time.perf_counter()
logits = model(tensor); probs = softmax(logits)
torch.cuda.synchronize()        # 等推理真正算完
latency = time.perf_counter() - t0
```

**最终实测**（ViT-B/16，batch=1，224×224，AMP）：

| 指标 | 首次 | 稳态 | NFR-01 上限 |
| --- | --- | --- | --- |
| 纯推理 `latency_ms` | 26.5 ms | **12.8—13.7 ms** | 300 ms ✅ |
| 端到端（HTTP 往返） | 87.8 ms | **32.5—35 ms** | 1500 ms ✅ |

与 M2-6 离线实测的 10.14 ms 吻合，说明在线/离线口径已一致。

### 7.6 ⚠️ 原地修改数组会"顺手毁掉"已算好的产物（已踩，已修）

**陷阱**：`ml/evaluate.py` 为筛出"最易混淆类别对"，对混淆矩阵执行了原地清零：

```python
np.fill_diagonal(cm, 0)          # ❌ 原地修改
flat = np.argsort(cm.ravel())    # 之后的 cm 已不是混淆矩阵
...
plot_confusion(cm, ...)          # 画出来的图对角线全是 0
payload["confusion_matrix"] = cm.tolist()   # 存下来的也是对角线为 0 的矩阵
```

后果非常隐蔽：**准确率指标全都正确**（Top-1/混淆对/sklearn 报告都正常），
但**报告里的 4 张混淆矩阵图呈现"没有任何正确预测"**，数据接口返回的矩阵也无法验证。
所有端到端冒烟（82 项）都没抓到它 —— 因为冒烟只检查了矩阵"是 102×102"，没检查内容自洽。

**被抓到的原因**：M3-8 的 pytest 断言了不变量
"对角线之和 == Top-1 命中数"，才暴露 `sum(diag) == 0`。

**修复**：在副本上清零，保留原始矩阵：

```python
cm_errors = cm.copy()
np.fill_diagonal(cm_errors, 0)      # ✅ 只动副本
```

**修复后不变量核验**（4 个模型全部成立）：

| 模型 | 对角线之和 | 期望（Top-1 命中数） | 非对角错误数 | 总数 − 对角线 |
| --- | --- | --- | --- | --- |
| ViT-B/16 | 6124 | 6124 | 25 | 25 |
| ConvNeXt-Tiny | 6116 | 6116 | 33 | 33 |
| ResNet-50 | 5796 | 5796 | 353 | 353 |
| EfficientNet-B0 | 5649 | 5649 | 500 | 500 |

**通用教训**：对 numpy 数组做统计用途的破坏性变换前，先 `.copy()`；
并给"派生指标"补一条**恒等式断言**（如 `sum(diag) == hits`），
否则错误会安静地流进图表与报告。

**同时产生的动作**：重新评估 4 个模型 → 重绘混淆矩阵图 → 重导 `metrics.json`
（指标数值未变，仅矩阵与图被修正）。

### 7.7 ⚠️ npm / esbuild 在本机需要放宽沙箱权限（已踩）

前端构建链有两处会被受限沙箱拒绝，且报错信息都指向"权限"而非真正的机制原因。

#### 坑 A：npm 缓存目录在 C 盘受限路径 → `EPERM: open '_cacache/tmp/...'`

npm 默认缓存 `C:\Users\<user>\AppData\Local\npm-cache`，写入被拒。
**注意**：用 `.npmrc` 里的 `cache=` 设置会**静默失效** ——
本项目路径含空格（`.../Flower Recognition System/...`），npm 的 ini 解析会把空格后的部分截断，
`npm config get cache` 仍返回 C 盘默认值。**必须用环境变量**：

```powershell
$env:npm_config_cache = "<项目根>\.cache\npm"
```

已固化在 `scripts/frontend.ps1` 里。

#### 坑 B：`registry.npmjs.org` 不可达

TLS 握手超时（与 huggingface.co 同一现象）。必须走镜像：
`registry=https://registry.npmmirror.com/`（已写入 `frontend/.npmrc`）。

#### 坑 C：`npm install` 的 postinstall 与 `vite build` 直接 `spawn EPERM` ❌→✅

**现象**：

* `npm install` 在 `arborist/rebuild.js → runScript → promise-spawn → ChildProcess.spawn`
  处报 `EPERM`；
* `npx vite build` 在 `esbuild/lib/main.js:ensureServiceIsRunning` 处报 `spawn EPERM`。

**根因**：受限沙箱禁止子进程使用**管道 stdio**（Node `child_process` 默认 `stdio:'pipe'`
需要命名管道）。esbuild 的 Node API 必须以子进程方式启动原生二进制并捕获其输出。

**两种处理方式**（按优先级）：

1. **规避**：`npm install --ignore-scripts` 跳过生命周期脚本，安装本身可正常完成
   （实测 105 个包 / 39 秒成功）。
2. **必须执行构建时升级权限**：`vite build` 无法规避，需以更宽权限运行一次
   （本机实测升级后 `✓ built in 15.98s` 成功产出 `frontend/dist`）。

**对项目的影响与对策**：

* 日常用 **`scripts/frontend.ps1 -Action install | build | dev`**，它已把缓存与镜像处理好；
  `-Action build` 若报 `spawn EPERM`，需要放宽权限重跑一次。
* ⭐ **答辩演示建议走"生产静态托管"路线**（M5-2）：由 FastAPI 直接托管 `frontend/dist`，
  单端口访问，**运行期完全不需要 esbuild/Vite**，也就不再受此限制影响。
  开发期的 `vite dev` 才需要该权限。

#### 坑 D：npm 缓存被中断的安装写坏

上一次 `npm install` 被中途杀掉，会留下**索引指向不存在内容文件**的损坏缓存，
后续 install 报 `ENOENT ... _cacache/content-v2/...`。
处理：删除 `node_modules` 与 `.cache/npm/_cacache` 后重装（实测恢复正常）。

#### 构建体积观察

完整引入 Element Plus 与 ECharts 后：

| 产物 | 原始 | gzip |
| --- | --- | --- |
| `index-*.js`（Vue + Element Plus + 业务） | 1091.9 KB | ~370 KB |
| `useEcharts-*.js`（ECharts） | 1012.4 KB | ~343 KB |
| `index-*.css` | 354.4 KB | ~49 KB |
| **合计** | **2.44 MB** | **约 0.76 MB** |

本地演示完全够用；若需优化可改为 Element Plus 按需引入（`unplugin-vue-components`）
与 ECharts 按需注册。当前不做，避免增加构建复杂度。

### 7.8 ⚠️ 无头浏览器验证：两个坑（已踩，已解决）

前端写完必须**真正渲染一次**才知道有没有运行时错误（类型检查与构建都查不出）。
本机用无头 Edge 做这件事，遇到两个坑：

#### 坑 A：`--user-data-dir` 路径含空格会被拆成两个参数

工作区路径含空格，写成 `--user-data-dir=D:\...\Flower Recognition System\...` 时
Chromium 会把空格后的部分当成**第二个 URL**，于是报
`Multiple targets are not supported in headless mode`，并悄悄退回默认配置目录
（`C:\Users\<user>\AppData\Local\Microsoft\Edge\User Data`），那里又被沙箱拒绝写入。

→ 修复：给参数值**加引号**：`--user-data-dir="D:\...\Flower Recognition System\..."`
（这是本项目第三次踩到"路径含空格"这个坑，见 §7.1 / §7.7）。

#### 坑 B：Chromium 多进程渲染依赖命名管道 → 受限沙箱下静默失败

表现非常隐蔽：Edge 进程**确实启动了 11 个**，但 `--screenshot` 不生成文件、
`--dump-dom` 输出 0 字节、stderr 也没有有效信息。

→ 原因同 §7.7 的 esbuild：Chromium 的渲染/GPU/工具进程之间用**命名管道**做 IPC，
受限沙箱禁止该机制。

→ 处理：执行渲染验证时需放宽一次权限（本会话实测放宽后立刻正常）。

#### 补充发现：本机 `--dump-dom` 无效，`--screenshot` 可用

实测三种写法，`--dump-dom` 无论 stdout 到文件还是到变量都产出 0 字节，
而 `--screenshot` 稳定可用（619 KB PNG）。
**因此本项目的渲染验证采用"截图 + 目视核验"，而不是 DOM 文本断言**，
证据反而更强（能看到真实布局与数据）。

#### 未登录页面可以直接截图，登录后页面必须走 CDP

命令行截图无法注入 localStorage，因此拿不到登录后的核心页面。
解决：用 **Chrome DevTools Protocol** —— 启动时加 `--remote-debugging-port`，
再通过 WebSocket 发送 `Runtime.evaluate` 写入 token，然后 `Page.captureScreenshot`。
已封装为 [`scripts/verify_frontend.py`](../scripts/verify_frontend.py)，可重复执行。

**验证结论**：12 个页面全部渲染正常；未登录访问 `/recognize` 与 `/login` 的截图
**SHA256 完全相同**，证明路由守卫确实生效。
