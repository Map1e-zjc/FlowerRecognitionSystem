## ADR-001 · 交付形态：Web 系统

- **结论**：做成浏览器访问的 Web 系统，核心交互是"上传图片 → 返回 Top-5 结果"。
- **理由**：答辩演示观感最好；前后端分离能体现工程完整度；跨设备访问，无需安装。
- **被否决**：桌面 GUI（Tkinter/PyQt，观感与工程度偏弱）、移动端 App（打包适配成本高，2—4 周内风险大）。

## ADR-002 · 技术栈：PyTorch + FastAPI + Vue3

- **结论**：训练与推理用 PyTorch + torchvision + timm；后端 FastAPI + SQLAlchemy + SQLite；前端 Vue3 + Vite + TypeScript + Element Plus + ECharts。
- **理由**：PyTorch 迁移学习生态最成熟、论文与教程最多，出问题易查；FastAPI 自带 OpenAPI 文档（`/docs` 可直接当答辩演示素材）；Vue3 上手快、中文资料多。
- **被否决**：Flask + 原生 HTML（工程度不足，做大屏可视化吃力）、TensorFlow/Keras（与 Flowers-102 主流权重生态不如 torch）。

## ADR-003 · 数据集：Oxford Flowers-102

- **结论**：使用 Oxford 102 Category Flower Dataset（8189 张，102 类），采用官方划分。
- **理由**：学术界标准基准，结果可复现、可与其他工作对比；规模适中，8 GB 显存在 2—4 周内能完成多模型对比训练。
- **被否决**：完全自建数据集（采集 + 标注耗时最长，精度风险高，周期不允许）；公开 + 自采混合（作为**可选扩展**保留，时间充裕再加入）。

## ADR-004 · 功能范围

- **结论**：包含 ①图片上传识别 + Top-5 置信度 ②花卉百科/养护知识库 ③识别历史记录 ④用户登录注册 ⑤模型对比与可视化 ⑥完整训练脚本 + 实验报告。
- **被否决**：摄像头实时拍照识别（浏览器摄像头在答辩环境不稳定，列为可选加分项）；管理员后台（ADR-007 已定为单角色，不做）。

## ADR-005 · 运行环境：本机 GPU

- **结论**：使用本机 NVIDIA GeForce RTX 4060 Laptop GPU（8 GB 显存，驱动 610.88）训练与推理演示。
- **理由**：零云成本；本机算力足够 —— Flowers-102 官方训练集仅 1020 张，单模型 60 epoch 预计 20—90 分钟。
- **风险提示**：8 GB 显存对 ViT-B/16 偏紧，需用 AMP + 较小 batch（见 03 文档显存预算表）。

## ADR-006 · 环境隔离：D 盘 venv + CUDA 版 PyTorch

- **结论**：在项目根目录创建 `.venv`（位于 D 盘），在其中安装 CUDA 版 PyTorch；`PIP_CACHE_DIR`、`TORCH_HOME`、`HF_HOME` 全部重定向到 D 盘。
- **理由**：**实测 C 盘仅剩 14.6 GB，D 盘剩 103.4 GB**。CUDA 版 torch wheel 约 2.5 GB，加上解包与预训练权重（再加约 1—2 GB）极易撑爆系统盘；全局环境当前是 `torch 2.14.0+cpu`（`cuda.is_available() == False`），不能用于 GPU 训练。
- **被否决**：使用现有全局 CPU 版 torch（训练慢数倍，2—4 周内跑不完多模型对比）。

## ADR-007 · 用户体系：SQLite + JWT 单角色

- **结论**：注册 / 登录（用户名 + 密码，bcrypt 哈希）/ JWT Bearer Token；单一"普通用户"角色，无管理员。
- **理由**：满足"登录后使用识别与历史记录"的答辩要求，成本最低。
- **被否决**：管理员角色 + 后台管理页（额外 3—5 天工作量）；完全不做登录（已由 ADR-004 否定）。

## ADR-008 · 部署：本机一键启动脚本

- **结论**：提供 PowerShell 启动脚本，同时拉起 FastAPI 与前端；另提供生产构建模式（`vite build` 产物由 FastAPI 静态托管）。
- **理由**：答辩现场只需双击一个脚本；Windows 下 Docker 的 GPU 透传配置麻烦且耗时。
- **被否决**：Docker Compose 容器化（列为可选，不占用主线时间）。

## ADR-009 · 周期：21 个工作日

- **结论**：按 M1（3 天）→ M2（6 天）→ M3（3 天）→ M4（4 天）→ M5（3 天）排期，留 2 天缓冲。
- **理由**：匹配 2—4 周窗口，且每个里程碑都有可独立验收的产出物。

## ADR-010 · 数据库：SQLite

- **结论**：使用 SQLite 单文件数据库，通过 SQLAlchemy ORM 访问。
- **理由**：单机演示、零运维；ORM 层已抽象，后续换 PostgreSQL 只需改连接串。

## ADR-011 · 数据集来源：HuggingFace 镜像（⚠️ 执行中变更）

- **原计划**：从官方 `www.robots.ox.ac.uk` 下载 `102flowers.tgz` + `imagelabels.mat` + `setid.mat`。
- **实际触发**：M1-5 执行时该域名**在本机无法解析** —— 本地 DNS 返回 `SERVFAIL`
  （其他域名如 pypi 清华源、download.pytorch.org、hf-mirror.com 均正常），
  换用阿里 / 腾讯 / Google / Cloudflare 公共 DNS 查询则全部超时（UDP 53 被限制）。
  即官方源在本网络环境下**不可达**，属计划中 R3 风险的实例化。
- **新结论**：改用 `hf-mirror.com` 上的 `dpdl-benchmark/oxford_flowers102`（parquet 封装）。
- **为什么这个镜像可接受**：它的三个划分规模与官方完全一致（1020 / 1020 / 6149）、
  102 类标签一致，因此**实验结论仍然与论文可比**，报告中需注明数据来源与封装形式。
- **代价**：需要 `pyarrow` 依赖；parquet 内图片体积明显大于官方 tgz
  （train 分片 398 MB / 1020 张 ≈ 390 KB 每张），转换后 jpg 约 3 GB，需额外磁盘与转换时间。
- **保留**：官方源代码路径仍在 `ml/download_data.py` 中（`--source oxford`），
  换到可访问 ox.ac.uk 的网络时可直接使用。

## ADR-012 · PyTorch 安装源：上海交大镜像索引（⚠️ 执行中变更）

- **原计划**：`pip install torch torchvision --index-url https://download.pytorch.org/whl/cu126`。
- **实际触发**：该源 DNS 可解析、HTTPS 可建连（HTTP 200），但下载阶段**完全停滞**
  （pip 缓存 45 秒零增长、无任何进度），无法在可接受时间内完成传输。
- **新结论**：改用 `https://mirror.sjtu.edu.cn/pytorch-wheels/cu126` —— 标准 PEP 503 索引，
  经探测含 cp312 + win_amd64 的 torch 2.6—2.14 与 torchvision 0.21—0.29 全套 wheel。
- **配套调整**：pip 的依赖解析阶段也曾停滞（20 余个 `pip-metadata-*` 目录、`pip-install-*` 全为 0 MB），
  因此改为**两步安装**：
  1. `pip install --no-deps --index-url <SJTU> "torch==2.14.0+cu126" "torchvision==0.29.0+cu126"`；
  2. 其余依赖单独从清华源安装。
  每步的网络操作都可预期，避免一次性大解析卡死。
- **实测**：torch wheel 实际大小 **2602.8 MB**（原估算 2.5 GB，吻合）。

## ADR-013 · 数据集清单格式：manifest.json（🔸 由 ADR-011 推导）

- **结论**：`ml/download_data.py` 无论从哪个源下载，最终都产出
  `data/flowers-102/manifest.json`（划分 + 0-based 标签的唯一权威来源）；
  训练 / 评估代码只读 manifest，不再直接解析 `.mat`。
- **理由**：两个数据源的原始标注格式完全不同（`.mat` vs parquet），
  加一层标准化清单后，`ml/dataset.py` 与数据源解耦，换源不需要动训练代码。
- **附带收益**：标签 1-based → 0-based 的转换只在下载器里做一次，杜绝各处重复转换导致的错位。

## ADR-014 · timm 预训练权重必须走 HuggingFace 镜像（⚠️ 执行中变更）

- **触发**：本机 `huggingface.co` 直连超时（WinError 10060），而 M2 要用 timm 的
  EfficientNet-B0 / ConvNeXt-Tiny / ViT-B/16，其预训练权重全部托管在 HuggingFace Hub。
- **结论**：所有训练/推理进程必须设置 `HF_ENDPOINT=https://hf-mirror.com`。
  已写入 `scripts/activate.ps1`、`scripts/train.ps1`、`scripts/train_all.ps1` 与 `ml/configs` 的调用链，
  不依赖人工记忆。
- **实测可达性**：`timm/convnext_tiny.fb_in22k_ft_in1k` 114.4 MB ✅、
  `timm/vit_base_patch16_224.augreg_in21k_ft_in1k` 346.3 MB ✅；
  torchvision 的 ResNet-50 权重走 `download.pytorch.org`（97.8 MB）✅ 可正常下载。
- **踩坑记录**：`tf_efficientnet_b0` 这个**裸名字**在 Hub 上没有对应仓库（直接探测 404），
  但 timm 会把它解析到 `timm/tf_efficientnet_b0.ns_jft_in1k`（该仓库存在）。
  即「探测裸仓库名 404」不代表模型不可用，必须以 timm 解析出的 `hf_hub_id` 为准。

## ADR-015 · 标签顺序已通过"元数据 + 视觉"双重校验（✅ 已验证）

- **为什么必须验证**：本项目全部中文名与百科信息都以 `class_id ∈ [0,101]` 为索引。
  若数据源的标签顺序与项目内置 `CLASS_NAMES_EN` 不一致，会导致**所有花名系统性错位**，
  而且训练指标看不出任何异常 —— 属于最难查的一类 bug。
- **证据 1（元数据）**：HF parquet 的 `huggingface` 元数据带 `ClassLabel.names`，
  与内置表逐项比对：**101/102 逐字相同**，唯一差异是 index 59 源侧写成
  `"pink-yellow dahlia?"`（多一个问号），属无害差异。
- **证据 2（视觉）**：抽取 12 个外观高辨识度类别（玉米罂粟、水仙、向日葵、玫瑰、荷花、
  油点草、鹤望兰、蓝盆花、射干、蓝花、沙漠玫瑰、锦葵）拼图人工核对，**12/12 全部正确**。
- **产出**：`ml/outputs/figures/label_order_check.png`（可滑入报告作为数据质量佐证）。
- **常态防护**：`ml/dataset.py::load_manifest()` 每次加载清单都会做规范化比对，
  一旦顺序不一致立即打印中文告警且 `_self_check` 直接失败返回 1，避免带病训练。
